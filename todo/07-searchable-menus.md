# 07 — Searchable menus

## Current status (2026-10-04)

Erbium's action menu wrappers do not yet expose filter-provider/input/list parts. The installed Base UI Menu declarations reviewed here do not export the filtering API described in the source-checkout research below. Treat that research as a snapshot; verify the installed release before building against it.

Command still imports `cmdk`, but the current roadmap is to replace it with Base UI command/autocomplete behavior. Confirm the upstream API and migration path first; the earlier recommendation to retain `cmdk` is superseded. Keep command palettes, action menus, and value pickers semantically distinct.

## Goal

Offer an optional, flush `CommandInput`-style filter header at the top of choice and action popups that benefit from search. Keep the input and its full-width separator fixed above the scrolling results. Status and priority pickers are the first product examples. An ordinary popup must keep its existing API, appearance, roles, and keyboard behavior when the filter is absent.

## Historical source-checkout research (2026-10-02)

The Base UI source checkout is at `b82a7d2cd` (2026-10-01). Its `packages/react/package.json` reports 1.8.0, and Erbium's `packages/ui/package.json` declares `^1.8.0`. The checkout now has a first-class **filterable Menu** API. This resolves the original proposal to replace action menus with Combobox: keep Menu for actions, links, checkboxes, radio items, and submenus; keep Combobox for value selection. No shared Combobox replacement or new Base UI primitive is indicated by the source reviewed here.

Base UI's pattern is `Menu.FilterProvider` around `Menu.Root`, with `Menu.Input`, optional `Menu.Clear` and `Menu.Empty`, and `Menu.List` inside `Menu.Popup`. Each searchable `Menu.SubmenuRoot` gets its own provider. `Menu.Popup` becomes a `dialog`, `Menu.Input` is a `searchbox` with `aria-controls` and `aria-activedescendant`, and `Menu.List` retains `role="menu"`; item roles stay appropriate to their action, checkbox, or radio behavior. The input owns focus while arrows move the highlighted item. Base UI handles IME composition, filtered highlight changes, nested menu handoff, and query clearing on close (including exit transitions). It does not focus the input when a menu opens by hover, touch, or pen. See the Base UI source references: Menu filtering guide (`base-ui/docs/src/app/(docs)/react/components/menu/page.mdx`), filter demo (`base-ui/docs/src/app/(docs)/react/components/menu/demos/filter/tailwind/index.tsx`), and provider options (`base-ui/packages/react/src/menu/filter-provider/MenuFilterProviderOptions.ts`).

The provider supports a controlled `value`/`onValueChange`, `defaultValue`, `autoHighlight`, `locale`, a custom `filter(text, trimmedQuery)`, and `filter={null}` for externally filtered or asynchronous results. Default matching contains the query while ignoring case, accents, and punctuation. Items can override matched text with `label`; empty groups are hidden and `Menu.Empty` displays when no items match. A controlled query must honor the close reset if that is the desired behavior. `Menu.useFilter` is available for external matching.

### Effect on current Erbium abstractions

| Surface       | Current abstraction                                                                                                                                         | Direction                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Dropdown menu | `DropdownMenuContent` puts all children in one `ScrollArea` inside Base UI `Menu.Popup`. Items, checkbox/radio groups, and submenus already use Menu parts. | Add an opt-in filter composition using `Menu.FilterProvider`, `Menu.Input`, `Menu.Empty`, and `Menu.List`. The header must be a direct fixed child of the popup; only `Menu.List` and its items belong in the `ScrollArea`. Existing unfiltered compositions remain valid.                                                                                                                                         |
| Context menu  | `ContextMenuContent` has the same all-children scroll structure and uses Base UI Context Menu parts.                                                        | Base UI `ContextMenu.Root` internally renders `Menu.Root`, and its popup/items are Menu parts, but `@base-ui/react/context-menu` does not export filter parts. Investigate an Erbium adapter that uses `Menu.FilterProvider` and Menu filter parts with the Context Menu root. Verify right-click, keyboard context key, long-press, pointer anchor, and input focus in a prototype before calling this supported. |
| Menubar       | Each `MenubarMenu` is a dropdown Menu root; `MenubarContent` reuses `DropdownMenuContent`.                                                                  | Apply the provider per searchable `MenubarMenu`, reuse the dropdown filter layout, and verify horizontal sibling navigation and hover switching while an input owns focus. Do not put one provider around the entire menubar.                                                                                                                                                                                      |
| Submenu       | Dropdown, context, and menubar wrappers render `Menu.SubmenuRoot` and reuse the content scroll layout.                                                      | Filter a submenu only when it has its own provider and input/list composition. A plain submenu inside a filtered parent remains plain. Test both directions of keyboard and pointer handoff, including RTL.                                                                                                                                                                                                        |
| Select        | Uses Base UI Select with a scrollable popup and no query model.                                                                                             | Keep Select for simple value pickers. Use Erbium Combobox for a searchable value picker so query and selected value stay separate; do not force Select or action Menu to become Combobox.                                                                                                                                                                                                                          |
| Combobox      | Already has `ComboboxSearchInput` with a flush icon/input/separator header and a separate scrollable `ComboboxList`.                                        | Reuse its visual measurements and behavior for searchable value pickers. Do not duplicate its listbox semantics in action menus.                                                                                                                                                                                                                                                                                   |
| Command       | `cmdk` owns command-palette filtering/navigation; `CommandInput` already provides the target flush header styling.                                          | Replace `cmdk` after verifying a supported Base UI command/autocomplete composition. Reuse visual conventions without conflating command, menu, and picker semantics.                                                                                                                                                                                                                                              |

The current dropdown/context content wrappers always wrap `children` in `ScrollArea`, so inserting `Menu.Input` as an ordinary child would scroll the header and leave items outside the required `Menu.List`. The implementation needs an explicit opt-in content structure or searchable variant that exposes a fixed header and a scrollable list while preserving `className`, refs, `render`, `data-slot`, positioning props, item APIs, and unfiltered use. The header should use the existing 40px search row, icon, full-width `Separator`, surface, and spacing from `CommandInput`/`ComboboxSearchInput`; `ScrollArea` keeps its vertical fades and thin scrollbar. Determine whether `Menu.List` should be rendered as the scroll viewport through `render`, or as a child of that viewport, and verify scrolling plus `aria-controls` targeting. Place `Menu.Empty` where it remains visible when there are no matches.

### Boundaries and open questions

- Base UI's built-in filtering hides matching item elements and empty groups; separator visibility still needs a design decision for filtered groups. The upstream demo styles separators conditionally, so check Erbium's group and separator composition rather than assuming automatic cleanup.
- Matching uses an item's text or `label`; define when consumers should supply `label` for icons, shortcuts, aliases, or translated text. Product-specific keywords and remote search stay with the consuming app, using controlled query and `filter={null}` when it renders the results itself.
- The source indicates checkbox and radio items retain their roles and state while filtered. Verify links (`Menu.LinkItem`), disabled items, close-on-select, selected values outside the current match, and submenu triggers in Erbium's wrapper API and examples.
- Context Menu's filter parts are inherited through Menu internally but are not re-exported from its package entry point. Confirm the mixed composition with typechecking and manual interaction checks before exposing a public searchable context menu API.
- Decide the public opt-in API after prototyping: explicit `DropdownMenuFilterProvider`/`DropdownMenuInput`/`DropdownMenuList` parts, or a dedicated searchable content variant. Keep the same pattern across dropdown, context menu, and menubar where the underlying behavior is proven. A `searchable` boolean alone cannot supply an accessible input name or controlled query API.

## Acceptance and implementation gate

1. Prototype a searchable action dropdown with an action, link, checkbox, radio group, disabled item, and both filtered and plain submenus using Base UI Menu filtering. Confirm roles, focus, activation, close/reset, group/separator visibility, and empty state.
2. Prototype a searchable status or priority value picker with the existing Combobox popup input. Confirm selected value versus temporary query, close reset, keyboard navigation, and screen-reader output.
3. Prototype the mixed Context Menu composition and a per-root filtered Menubar menu. Check right-click and keyboard opening, pointer positioning, long-press, sibling navigation, hover, touch, RTL, and IME.
4. Specify the optional Erbium compound API and fixed header/list layout. Keep existing unfiltered wrappers source-compatible and visually unchanged; add only the shared styling/composition needed by the accepted prototypes.
5. Add Storybook examples and verify their interactions manually, regenerate the affected registries, and run `bun run check` when implementation is authorized.

This document records research and proposed implementation work. It does not authorize Base UI or Erbium primitive changes by itself.
